# 03. ローカライズ初回プロンプトガイド

> GDR フレームワークをプロジェクトに導入する際の「最初の一言」をどう伝えるか。
> 前提知識: [01. GDR とは](/01_GDR/01_GENERAL_DECISION_RECORD.md) / [02. AI-Driven GDR ビルドアップ](/01_GDR/02_AI_DRIVEN_GDR_BUILDUP.md)

## 1. ローカライズとは

GDR フレームワーク自体は scope や PREFIX の具体的な定義に依存しない汎用設計である。**ローカライズ**とは、この汎用フレームワークを特定のプロジェクトに合わせてカスタマイズする作業を指す。

具体的には以下を決定する:

- プロジェクトで使う **scope**（影響領域の分類）
- プロジェクトで使う **PREFIX**（ドメイン識別子）
- GDR の **出力先**（ディレクトリ構成）
- **短縮キーワード** などの運用設定

これらの決定自体が最初の GDR（例: `GDR-META-001`）になる。

## 2. 推奨プロンプト

```
GDRを導入する。以下のプロジェクト情報をもとに前提定義書を作成して。

プロジェクト名: {プロジェクト名}
ドメイン: {ソフトウェア / 製造 / 医療 / 金融 / その他}
概要: {プロジェクトの概要を1〜3文で}
主な関心事: {例: API設計、画面UI、運用ルール、コスト管理 など}
GDR出力先: notes/{01_spec,05_knowledge,10_things,20_kaizen,80_bug_fix_report,91_gdr,99_other}/

短縮キーワード:
  "改善提案[：|；][タイトル]": notes/20_kaizen/ 配下に T2 テンプレートの構成に従って改善提案文書を生成
  "レビュー[：|；][ファイル名]": 同位置にファイル名_reviewedとしてレビュー文書を生成
  "レビュー反映[：|；][ファイル名]": _reviewedの内容を元ファイルに組み込み、_reviewedを削除
  "バグレポート[：|；][ファイル名]": notes/80_bug_fix_report/ 配下にバグレポートを作成
  {プロジェクト固有のキーワードを追加}
```

> **出力先について:** 上記は §2.2 の標準構成を採用したテンプレート。プロジェクト固有の慣行（`documents/decisions/` など）がある場合はそれを優先してよい。

このプロンプトにより AI は:

- [T1_CONTEXT_DEFINITIONS.md](/01_GDR/templates/T1_CONTEXT_DEFINITIONS.md) テンプレートに基づいた前提定義書を生成する
- [scope ガイド](/01_GDR/guide/01_SCOPE_GUIDE.md) / [PREFIX ガイド](/01_GDR/guide/02_PREFIX_GUIDE.md) を参照してプロジェクトに適した scope・PREFIX を提案する
- 出力先ディレクトリの構成を提案する
- CLAUDE.md の `コンテキスト短縮用キーワード` セクションを生成する

### 2.1. GDR 出力先の書式

`mkdir` コマンドと同じ感覚でディレクトリを指定する。スペース区切りで複数指定でき、ブレース展開も使える。

```
# スペース区切りで複数指定
GDR出力先: documents/decisions/ documents/kaizen/ documents/bug_fix_report/

# ブレース展開で共通プレフィックスをまとめる
GDR出力先: documents/{decisions,kaizen,bug_fix_report}/
```

AI は指定されたディレクトリごとに用途を推測し、前提定義書の出力先テーブルとして整理する。

### 2.2. 推奨ディレクトリ構成

GDR フレームワーク自体は出力先に依存しないが、新規プロジェクトで迷う場合は **`notes/` 直下に番号プレフィックス付きの 7 種 + 退避領域 `_archive/`** を配置する標準構成を推奨する。番号は表示順、サフィックスはバケットの用途を示す。

| ディレクトリ | 用途 | 主な出力元 |
|---|---|---|
| `notes/01_spec/` | 仕様書 | 機能仕様・API 契約・データモデルの起草と更新 |
| `notes/05_knowledge/` | 知見ストック | 調査メモ、技術選定の参考、ベストプラクティス |
| `notes/10_things/` | 横断トピック | 単一仕様に収まらないテーマの議論ドラフト |
| `notes/20_kaizen/` | 改善提案 | `改善提案：` `API設計：` `マイグレーション：` の出力先 |
| `notes/80_bug_fix_report/` | バグ修正レポート | `バグレポート：` の出力先 |
| `notes/91_gdr/` | GDR メタ・records・reference | 前提定義書 / `INDEX.md` / `gdr/`（GDR レコード） / `_reference/`（上流テンプレート） / `review/`（横断レビュー） |
| `notes/99_other/` | その他 | 上記に当てはまらないメモ |
| `notes/_archive/` | 退避領域（**AI デフォルト除外**） | `アーカイブ：` `/gdr-archive` の出力先。元のパス構造を保ったまま退避（`notes/_archive/20_kaizen/...`） |

番号体系は「01〜09: 仕様系 / 10〜19: 横断 / 20〜79: 提案系 / 80〜89: 報告系 / 90〜99: メタ系」のような余白を残してある。プロジェクト固有の追加バケット（例: `40_design/` `60_review/`）は同じ番号原則で配置する。`_` プレフィックスの `_archive/` は番号体系の外側に置き、AI セッション開始時の読み込み対象から除外する規約上のマーカーとして機能する。

**`notes/91_gdr/` 配下のサブ構造（推奨）:**

| パス | 役割 |
|---|---|
| `notes/91_gdr/00_CONTEXT_DEFINITIONS.md` | 前提定義書（[T1](/01_GDR/templates/T1_CONTEXT_DEFINITIONS.md) ベース） |
| `notes/91_gdr/INDEX.md` | GDR_INDEX（全 GDR レコードの一覧） |
| `notes/91_gdr/gdr/` | GDR レコード本体（PREFIX 単位 or 連番でファイル分割） |
| `notes/91_gdr/_reference/` | 上流リポジトリ（`yoshinag/general-decision-record`）から取得した**編集禁止スナップショット**。テンプレート / ガイドの参照用 |
| `notes/91_gdr/review/` | 複数 GDR や複数文書を横断するレビュー文書の出力先 |

`GDR出力先` の指定例:

```
GDR出力先: notes/{01_spec,05_knowledge,10_things,20_kaizen,80_bug_fix_report,91_gdr,99_other}/
```

> `_archive/` は退避時に自動作成されるため、`GDR出力先` に明示する必要はない。

### 2.3. プロジェクト直下 CLAUDE.md への退避領域の明記

`notes/_archive/` を AI が誤って読み込まないよう、プロジェクト直下 `CLAUDE.md` に明示の指示を 1 段落で書く。最小例:

```markdown
## ディレクトリ構成

- `notes/_archive/` は退避領域。**AI はセッション開始時にこのディレクトリを読み込まない**。ユーザーが個別ファイルのパスを明示指定した場合のみ参照する。物理削除はユーザー手動 (`rm`) で行う
```

Claude Code 利用者で技術的強制が必要な場合は `.claude/settings.json` の `hooks.PreToolUse` で `notes/_archive/` への `Read` を deny する雛形を追加できる（詳細は [05. Claude Code セットアップ](/01_GDR/guide/05_CLAUDE_CODE_SETUP.md) 末尾を参照）。

## 3. プロンプトの構成要素

| 要素 | 必須 | 目的 | 記述のコツ |
|---|---|---|---|
| プロジェクト名 | ○ | GDR の識別 | 正式名称でなくて良い |
| ドメイン | ○ | 業種別ガイドの参照 | 複数にまたがる場合はカンマ区切り |
| 概要 | ○ | scope・PREFIX 提案の文脈 | 1〜3 文で「何をするプロジェクトか」 |
| 主な関心事 | − | scope の優先順位付け | 意思決定が多い領域を列挙 |
| GDR 出力先 | − | ディレクトリ構成の決定 | スペース区切りまたはブレース展開で複数指定可。省略時は AI が提案 |
| 短縮キーワード | − | CLAUDE.md の短縮キーワード生成 | 既定 4 種（改善提案・レビュー・レビュー反映・バグレポート）＋プロジェクト固有を追加 |
| 既存の制約 | − | 提案の精度向上 | モノレポ構成、既存の ADR など |

## 4. 業種別の記述例

> 以下は代表的な 4 業種の記述例。**他業種**（医療 / 金融 / 教育 / ゲーム / インフラ・DevOps / 観光 等）も、同じプロンプト骨格（プロジェクト名 / ドメイン / 概要 / 主な関心事 / GDR 出力先 / 短縮キーワード）に [scope ガイド](/01_GDR/guide/01_SCOPE_GUIDE.md) と [PREFIX ガイド](/01_GDR/guide/02_PREFIX_GUIDE.md) の該当章を組み合わせれば展開可能。`ドメイン` 欄に複数業種をカンマ区切りで書けば、AI が両方の業種別 scope/PREFIX を提案する。

## 5. アンチパターン

| パターン | 問題 | 改善 |
|---|---|---|
| scope と PREFIX を自分で全部定義してから渡す | AI の構造化能力を活かせない。過剰定義になりやすい | 概要と関心事だけ渡し、AI に提案させる |
| プロジェクトの詳細を長文で書く | AI が情報過多で焦点を見失う | 1〜3 文の概要 + 関心事のキーワード列挙に絞る |
| ドメインを書かない | 業種別ガイドを参照できず、汎用的すぎる提案になる | 一言でよいのでドメインを明記する |
| 最初から完璧を目指す | ビルドアップの思想に反する。手が止まる | 粗くてよいので対話を始める。磨くのは後 |
